# PT7: Move work tracking to GitHub Issues

**Existing prompt scope:** P651, campaign tracking and release-evidence workflow.

**Status:** ready-for-agent for owner-directed tracker migration preparation. The current catalog remains authoritative until the verified cutover.

**Planning source:** [Approved proof-tooling repairs](../PRODUCT_MILESTONES.md#approved-proof-tooling-repair-tickets--2026-10-16).

**What to build:** The owner and agents use GitHub Issues as the work tracker, with the existing campaign's explicit IDs, completion history, evidence and dependencies preserved. Local machine-readable data and views remain usable as generated snapshots after cutover, with one writable authority.

**Blocked by:** None (can start immediately).

## Acceptance criteria

- [ ] Produce a reviewable migration inventory covering the existing 751 prompt IDs and these seven approved execution briefs, preserving parent relationships, completion states, readiness, evidence classes, release history and blocking edges.
- [ ] Import and verify the agreed records through an idempotent, resumable mapping from explicit domain IDs to GitHub issue numbers. Retries create no duplicates, and issue numbers never substitute for prompt IDs.
- [ ] Use supported native issue relationships and readiness labels where available, with an explicit representation for missing, partial and done. Importing records earns no new completion credit and changes no unrelated issue.
- [ ] Validate counts, statuses, dependencies, parent links and evidence against the source before cutover. Preserve a recoverable export and migration mapping; an interrupted or failed import leaves the existing tracker authoritative.
- [ ] At verified cutover, update agent/skill tracker instructions and the normal read/write workflow to use GitHub Issues. Generate the compatible local catalog and views from captured issue data rather than maintaining a second writable tracker; keep existing consumer interfaces stable where possible.
- [ ] Cover import retry, partial failure, mapping, export and round-trip equivalence with a small representative fixture, then reconcile the complete inventory. Retain private-source boundaries and existing credential/deployment safeguards.

## Testing and handoff boundary

Observe discriminating failures at the import/export and tracker-consumer seams before implementation. Separate preparation, verified import and authority cutover; use existing tooling and stable reader interfaces to contain the migration. A partial import or configuration-only change is not completion.

Return the exact source snapshot, GitHub mapping, reconciliation and recovery evidence, updated workflow and any unresolved scope. The tracker migration preserves campaign acceptance and grants no gameplay runtime restart or application release.
