# PT1: Preserve test failures when displaying logs

**Existing prompt scope:** P651, executable proof and release checks.

**Status:** ready-for-agent for this approved tooling repair; catalog completion is unchanged.

**Planning source:** [Approved proof-tooling repairs](../PRODUCT_MILESTONES.md#approved-proof-tooling-repair-tickets--2026-10-16).

**What to build:** A proof-test invocation displays useful diagnostics and returns the test process's actual result, so an owner or CI caller can distinguish a failing test from a passing test without reading the log manually.

**Blocked by:** None (can start immediately).

## Acceptance criteria

- [ ] A passing test returns zero; a failing test retains its nonzero exit status after its log excerpt is printed.
- [ ] An interrupted test produces a distinguishable non-success result, and diagnostic or cleanup failures preserve the original test failure.
- [ ] Intentional test-first RED remains a failing process result; the caller records its expected purpose separately.
- [ ] Adopt the safe invocation at the bounded proof-check entry points affected by the observed logging pattern and document its normal use.
- [ ] Focused automated coverage exercises passing, failing and interrupted child processes through the real invocation and diagnostic path; the existing CI path runs this coverage.

## Testing and handoff boundary

Observe the failing invocation regression before implementation, then validate the repaired invocation with small disposable child processes. Preserve the test-only commit and exact process results. Reuse existing command execution and CI facilities; this repair needs no gameplay runtime or application feature change.

Return the candidate, focused results, adopted invocation points and any remaining callers outside this bounded repair. Completing PT1 supplies tooling evidence to P651, not whole-prompt or gameplay completion.
