# PT4: Protect emulator allocations throughout startup

**Existing prompt scope:** P660 allocator lifecycle repair; P651 proof execution support.

**Playable release:** [PC10.3 — Resilient private sessions](../PRODUCT_MILESTONES.md#pc10-smaller-playable-releases--2026-10-16).

**Status:** ready-for-agent for this approved repair. P660's recorded completion and the other catalog states are unchanged by publication.

**Planning source:** [Approved proof-tooling repairs](../PRODUCT_MILESTONES.md#approved-proof-tooling-repair-tickets--2026-10-16).

**What to build:** A run that successfully allocates an emulator row retains its ownership while preparing startup, even when another worker updates the shared registry. A failed startup returns only that run's resources.

**Blocked by:** None (can start immediately).

## Acceptance criteria

- [ ] Establish the run's minimal ownership and configured-row reservation atomically through the existing shared registry and locking facilities.
- [ ] An interleaved unrelated registration or registry update preserves the allocated but not-yet-launched row and prevents a second owner from receiving it.
- [ ] Startup failure or cancellation releases only ownership/configuration created by this run, after the existing owned-process and port return checks.
- [ ] Preserve pre-existing configuration, other projects' entries and reservations, and pending or running foreign children. Routine work without a runtime allocation still uses the existing optional coordination policy.
- [ ] Cover allocation, interleaving, conflict and failed-start return with isolated registry/process fixtures, and run the focused coverage in the existing validation path.

## Testing and handoff boundary

Observe the allocation-loss regression before implementation. Use temporary registry fixtures and disposable owned processes rather than mutating another task's host-wide reservation. Keep the repair within the existing allocator lifecycle; broader coordination redesign is outside this brief.

Return the candidate, race/cleanup results and any retained owned resources. The checkpoint owner controls later gameplay allocations; publication creates no runtime grant or prompt closure credit.
